# ПРОМПТ ДЛЯ CURSOR: фронтенд ПМФК (сайт форума + ПМФК CONNECT)

Ты работаешь как senior/middle+ frontend-разработчик и архитектор. Твоя задача: с нуля построить production-grade фронтенд веб-приложения «ПМФК: Первый Московский Форум Коллабораций» (10 декабря 2026, Москва, арт-центр Linda de La). Приложение состоит из двух частей:

1. **Публичный сайт форума** (лендинг, 17 секций, SSG, SEO).
2. **ПМФК CONNECT** (закрытая платформа бизнес-знакомств: вход, профиль, лента, сохранённое, мэтчи, чат, встречи, билет и права доступа).

В корне проекта лежат два PDF с макетами и ТЗ. **Они являются единственным источником дизайна и контента** (Figma нет):

- `PMFK_2026_MOBILE_approval_RC3.pdf` (53 страницы, мобильная версия, 390 px)
- `PMFK_2026_WEB_approval_RC3.pdf` (45 страниц, десктоп, 1440 px)

Не придумывай дизайн и тексты. Бери их из PDF. Ниже описано, как с ними работать, какой стек и архитектуру использовать и в каком порядке делать.

## 0. Правила работы (обязательно)

1. **Сначала анализ, потом код.** Перед любой реализацией выполни раздел 1 (разбор макетов) и положи результат в `docs/design-analysis.md`.
2. **Работай этапами** (раздел 15). После каждого этапа: typecheck, lint, тесты, сборка проходят, делается отдельный осмысленный коммит (Conventional Commits). Не переходи к следующему этапу, пока предыдущий не зелёный.
3. **Не копируй баги макета** (раздел 1.4). Цель: «выглядит как макет, но без этих багов».
4. **Если данных не хватает** (нет API, нет ассетов, нет решения по поведению), не блокируйся и не угадывай молча: выбери разумное допущение из раздела 16, зафиксируй его в `docs/adr/` или `docs/assumptions.md` и иди дальше.
5. **Никаких хардкод-текстов в JSX** для лендинга: весь контент в типизированных объектах (раздел 8).
6. **Никаких `any`, `// @ts-ignore`, `eslint-disable` без комментария с причиной.**
7. Пиши код так, чтобы его мог принять другой разработчик: понятные имена, маленькие компоненты, публичные API слайсов, документация решений в ADR.
8. Весь UI-текст на русском. Идентификаторы, комментарии к коду и коммиты на английском.

## 1. Разбор макетов (первое действие)

### 1.1. Как читать PDF

- Страницы PDF это **скриншоты** локальной сборки (JPEG внутри ReportLab-PDF). Десктоп снят в 2880 px (retina ×2 от 1440), мобайл в 390 px (1×).
- Одна секция может занимать несколько страниц («Фрагмент 1 из 2»): это просто длинный экран, нарезанный по высоте. Склей мысленно в один экран.
- Извлеки изображения страниц (`pdfimages -j` или `pdftoppm -r 150`) в `docs/design/ref/{mobile,web}/` и сверяйся с ними при вёрстке. Извлеки текст (`pdftotext -layout`) для точного копирайта.
- Из PDF **можно и нужно** сэмплировать цвета (пиксели) для токенов, оценивать размеры отступов, радиусы, размеры шрифтов относительно ширины кадра (1440 / 390).
- Последняя страница каждого PDF это «Лист согласования», в проект не переносится.
- Надписи «РАСПИСАНИЕ ФОРМИРУЕТСЯ», «Время в работе», «Планируется», «Точный адрес уточняется» это **реальные состояния заглушек**, а не ошибки макета. Они управляются флагами (раздел 8.3).

### 1.2. Что должно получиться в `docs/design-analysis.md`

- Таблица всех экранов: название, роут, какие блоки, отличия mobile vs desktop.
- Список токенов дизайна (цвета, градиенты, радиусы, тени, типографика, отступы, брейкпоинты) с обоснованием, откуда взяты.
- Список переиспользуемых компонентов и вариантов (см. раздел 4).
- Список **пробелов в макете** (см. 1.3) и принятые решения по ним.
- Список багов макета (см. 1.4).

### 1.3. Чего нет в макете, и ты должен спроектировать сам (в рамках тех же токенов и стиля)

- Hover / focus-visible / active / disabled состояния всех интерактивных элементов.
- Loading (skeleton), empty, error состояния всех экранов CONNECT.
- **Экран ввода OTP-кода** после «Получить код на email» (поле на 6 цифр, таймер повторной отправки, ошибка неверного кода, лимит попыток).
- Выход из аккаунта, подтверждение удаления аккаунта (модалка).
- Планшетный адаптив (768–1024): в макете только 390 и 1440.
- Страницы 404, 500 и юридические страницы («Политика ПДн», «Согласие», «Публикация профиля»).
- Тосты (успех, ошибка, лимит запросов).
- Состояния сокета (переподключение, оффлайн) в чате.

### 1.4. Баги и недочёты макета (НЕ повторять)

- Слово рвётся посреди слова: «ПРОФЕССИОНАЛЬНЫ / Е СООБЩЕСТВА» на мобайле. Решение: `hyphens`, `text-wrap: balance`, `overflow-wrap: anywhere` только как страховка, подбор размера заголовка через `clamp()`.
- «НЕТ ДОСТУПА» на экране «Билет и права доступа» наезжает на абзац ниже (неверный line-height).
- В hero на мобайле sticky-CTA обрезает строку «10 декабря встречаемся лично…».
- На мобильной ленте панель действий (× ☆ «Хочу познакомиться») перекрывает текст карточки. Нужен нижний отступ контента на высоту панели и таб-бара плюс safe-area.
- Фиксированные панели (таб-бар, sticky-CTA) должны учитывать `env(safe-area-inset-bottom)` и `dvh`.
- Заголовки капсом на узких экранах не должны переполнять контейнер.

## 2. Стек

Обязательный:

- **Next.js (App Router), React, TypeScript `strict`** (+ `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` по возможности).
- **TanStack Query v5** для всего серверного состояния. TanStack Router/Start не использовать.
- **React Hook Form + Zod + @hookform/resolvers**.
- **Tailwind CSS v4** (токены в `@theme`) + `class-variance-authority` + `clsx` + `tailwind-merge`.
- **Radix UI primitives** (Dialog, Accordion, Checkbox, Select, Tabs, VisuallyHidden, Slot) и `sonner` для тостов. OTP: `input-otp`.
- **motion** (бывш. Framer Motion) с `LazyMotion` для reveal-анимаций; остальное на CSS.
- **nuqs** для URL-состояния (табы, фильтры, открытая модалка).
- **openapi-typescript + openapi-fetch**, если есть OpenAPI. Если нет, DTO-типы вручную в `shared/api/dto`.
- **MSW** (моки API и WebSocket) для dev, тестов и Playwright.
- **Качество:** ESLint (flat config) + `eslint-plugin-jsx-a11y` + `eslint-plugin-import` (no-cycle) + **Steiger** (линтер FSD), Prettier, lefthook (pre-commit), commitlint.
- **Тесты:** Vitest + Testing Library, Playwright (e2e), axe для a11y-проверок.
- **Документация UI:** Storybook (или Ladle) для `shared/ui`.
- **Наблюдаемость:** Sentry (с scrub персональных данных), Яндекс Метрика (подключается через компонент с согласием на cookies).
- **Env:** `@t3-oss/env-nextjs` + Zod (сборка падает при невалидных переменных).
- **Деплой:** `output: 'standalone'` + Dockerfile + `docker-compose` для локального запуска.

**Swiper в проекте не нужен**: в макете нет каруселей. Если появится слайдер, использовать `embla-carousel`. Если понадобятся swipe-карточки в ленте, делать на `motion` (drag), а не на Swiper.

Запрещено добавлять тяжёлые зависимости (moment, lodash целиком, UI-киты вроде MUI/Ant) без ADR с обоснованием.

## 3. Архитектура: Feature-Sliced Design (с послаблениями)

### 3.1. Решение

Используем FSD, но прагматично:

- **CONNECT** строим по FSD полностью (entities, features, widgets, pages).
- **Лендинг** это один слайс `pages/landing`; его секции лежат внутри слайса (`ui/sections/*`) и **не** выносятся в widgets.
- Слой `processes` **не используем**.
- Кросс-импорты между сущностями только через нотацию `@x` и только при реальной необходимости.

### 3.2. Интеграция с Next.js App Router

- В корне репозитория: `app/` (Next-роутинг) и пустая `pages/` с `README.md` (чтобы Next не подхватил `src/pages` как pages router).
- Файлы в `app/**` **тонкие**: `page.tsx` только `export { LandingPage as default } from '@/pages/landing'` + `metadata`/`generateMetadata`/`generateStaticParams`. Никакой логики и вёрстки.
- Весь код в `src/` по слоям FSD. Алиас `@/*` → `src/*`.

### 3.3. Структура

```
app/
  (site)/page.tsx                      # лендинг
  (site)/privacy/page.tsx              # политика ПДн
  (site)/consent/page.tsx              # согласие на обработку ПДн
  (site)/profile-publication/page.tsx  # согласие на публикацию профиля
  (connect)/connect/layout.tsx         # guard, провайдеры CONNECT (ws, shell)
  (connect)/connect/login/page.tsx
  (connect)/connect/profile/page.tsx
  (connect)/connect/feed/page.tsx
  (connect)/connect/saved/page.tsx
  (connect)/connect/matches/page.tsx
  (connect)/connect/matches/[matchId]/page.tsx
  (connect)/connect/meetings/page.tsx
  (connect)/connect/ticket/page.tsx
  api/                                 # BFF route handlers (auth, ws-ticket, proxy)
  not-found.tsx, error.tsx, global-error.tsx
pages/README.md
middleware.ts                          # guard /connect/*, noindex-заголовок

src/
  app/        # providers (QueryClient, Toaster, Motion), стили, шрифты, env
  pages/      # landing, legal, connect-login, connect-profile, connect-feed,
              # connect-saved, connect-matches, connect-chat, connect-meetings,
              # connect-ticket
  widgets/    # site-header, site-footer, connect-shell (sidebar / bottom-nav),
              # paywall-modal, chat-panel, profile-card-stack
  features/   # auth-by-email, edit-profile, delete-account, react-to-profile,
              # save-profile, send-message, propose-meeting, ticket-gate
  entities/   # viewer, profile, match, message, ticket-access, meeting
  shared/
    ui/       # дизайн-система
    api/      # http-client, ws-client, error model, dto/openapi
    lib/      # hooks, cn, format, a11y, safe-url
    config/   # env, routes, flags, site-meta
    content/  # типизированный контент (если не внутри pages/landing)
    styles/   # tokens.css, globals.css
```

Структура слайса: `ui/ model/ api/ lib/ config/ index.ts`. Наружу экспортируется только публичный API в `index.ts`.

### 3.4. Правила импортов (проверяются Steiger и ESLint)

- Слой импортирует только из нижележащих: `app → pages → widgets → features → entities → shared`.
- Слайсы одного слоя **не** импортируют друг друга (исключение: `@x` для entities).
- Импорт внутрь слайса только через его `index.ts`.
- `shared` не знает о доменах.
- Компоненты не вызывают `fetch` напрямую: только через `api/` слайса или `shared/api`.
- **Граница server/client:** по умолчанию серверные компоненты. `'use client'` ставится на минимально возможном узле. В `shared/ui` клиентскими делаем только интерактивные компоненты (Radix-обёртки, аккордеон, модалка).

## 4. Дизайн-система (`shared/ui`)

### 4.1. Токены (из макета, уточнить сэмплированием цветов из PDF)

Ориентиры (проверить и скорректировать пиксельным сэмплом):

- **Фон:** очень тёмный фиолетово-чёрный (≈ `#14001f` … `#0d0016`), страницы и секции с мягкими радиальными/линейными градиентами в фиолетовый (≈ `#5b0fd1`, `#2a0546`) и бордово-розовый.
- **Акцент:** оранжевый (≈ `#ff5a1f`), используется для акцентной части заголовков, основных кнопок, номеров (01/02/03), иконок, левой вертикальной полосы страницы.
- **Текст:** белый для заголовков, приглушённый сиренево-серый для абзацев, персиковый/бежевый (≈ `#f2b48a`) для eyebrow-меток и статусных подписей.
- **Поверхности:** полупрозрачные «стеклянные» карточки (`bg-white/5` на фиолетовом, тонкая 1 px граница `white/10`, радиус 24–32 px), модалки темнее и насыщеннее.
- **Градиенты:** фиолет → оранжево-красный для акцентных карточек («ПОРА ВСТРЕТИТЬСЯ», билет, «МЫ ЗАПУСКАЕМСЯ»), оранжевое свечение (glow-тень) под основной кнопкой.
- **Статусные:** янтарный баннер демо-режима, зелёный индикатор онлайна, красно-бордовый для ошибок.
- **Типографика:** заголовки капсом, очень жирные, плотные (Arimo/Helvetica-Bold-подобный grotesque), мелкий текст Noto Sans. Eyebrow: капс, трекинг `0.2em`, 11–12 px. Размеры заголовков через `clamp()`.
- **Радиусы:** `--radius-sm 12px`, `md 16px`, `lg 24px`, `xl 32px`, pill `9999px`.
- **Отступы:** шкала 4/8; контейнер лендинга ≈ 1100–1200 px по центру, боковые поля мобайл 16–24 px.
- **Брейкпоинты:** `sm 640`, `md 768`, `lg 1024`, `xl 1280`, макетные точки 390 и 1440.

Всё это лежит в `src/shared/styles/tokens.css` (`@theme`) и **нигде не дублируется** в компонентах. Градиенты и glow оформляются как utility/CSS-переменные.

### 4.2. Принципы построения компонентов

1. **Headless + стили:** поведение и a11y от Radix, внешний вид наш.
2. **Варианты через `cva`**, типизированные через `VariantProps`.
3. **API всех компонентов единообразен:**
   - всегда принимают и мержат `className` (`cn = twMerge(clsx(...))`);
   - пробрасывают `ref` и остальные DOM-атрибуты через spread;
   - `asChild` через Radix `Slot` там, где элемент может быть ссылкой или кнопкой;
   - состояния выражаются `data-*` атрибутами (`data-state`, `data-invalid`, `data-loading`), а не россыпью условных классов;
   - композиция вместо флагов: `Card`, `Card.Header`, `Card.Body`, `Card.Footer`.
4. Каждый компонент: `Component.tsx`, `Component.stories.tsx`, при необходимости `Component.test.tsx`, экспорт через `index.ts`.
5. Никаких «магических» значений: только токены.

### 4.3. Обязательный состав

`Button` (primary / secondary / ghost / link; sizes; `loading`; `iconLeft/Right`; `asChild`; `fullWidth`), `IconButton`, `Input`, `Textarea`, `Select`, `Checkbox`, `Field` (label + hint + error + `aria-describedby`), `TagToggle` / `TagGroup` (мульти-выбор с лимитом), `Badge` / `StatusPill`, `Card` (+ composition), `Modal` (на Radix Dialog; фокус-трап, закрытие по Esc/оверлею, возврат фокуса), `Accordion`, `Tabs`, `Toast` (sonner), `Skeleton`, `EmptyState`, `Avatar` (буква-плейсхолдер), `Container` / `Section` / `SectionHeader` (eyebrow `NN / НАЗВАНИЕ` + линия), `Heading` (капс + акцентная часть: `<Heading accent="ФОРУМ КОЛЛАБОРАЦИЙ">`), `GlassPanel`, `BottomNav`, `SidebarNav`, `ChatBubble`, `ChatInput`, `OtpInput`, `Logo` (SVG-знак из четырёх оранжевых скруглённых квадратов + вордмарк «ПМФК»; если векторного логотипа нет, воссоздать SVG по макету и пометить как временный).

Все компоненты должны быть доступны с клавиатуры, иметь видимый `:focus-visible`, корректные ARIA-роли и контраст не ниже WCAG AA (особенно приглушённый текст на тёмном фоне).

## 7. Данные и API

### 7.1. Разделение состояния

- **Серверное** только TanStack Query. Не дублировать в zustand/redux.
- **URL-состояние** через `nuqs`.
- **Локальное** `useState`/RHF.
- **Глобальное клиентское** минимально (маленький zustand только для UI: статус сокета, глобальные модалки). Если можно без него, без него.

### 7.2. HTTP-клиент (`shared/api`)

- Единая обёртка над `fetch` (или `openapi-fetch`) с `credentials: 'include'`, таймаутом, `AbortSignal`, ретраями только для идемпотентных запросов.
- Нормализация ошибок в `ApiError { status, code, message, fieldErrors?, requestId? }`.
- Глобальные реакции по кодам: `401` → сброс сессии и редирект на `/connect/login`; `403 TICKET_REQUIRED` → paywall-модалка; `429` → тост с «повторите через N секунд»; `5xx` → тост + Sentry.
- Тип контракта: если есть OpenAPI, генерация типов скриптом `pnpm api:types`. Если нет, `shared/api/dto/*` + файл `docs/api-contract.md` со списком ожидаемых эндпоинтов (Cursor должен его составить сам по экранам CONNECT: auth, viewer, profile CRUD, feed, save/unsave, interest, matches, messages, ticket access, meetings).

### 7.3. Query

- На каждый запрос фабрика `queryOptions`, ключи через фабрику ключей на сущность:

```ts
export const profileKeys = {
  all: ['profiles'] as const,
  feed: (f: FeedFilters) => [...profileKeys.all, 'feed', f] as const,
  saved: () => [...profileKeys.all, 'saved'] as const,
  me: () => [...profileKeys.all, 'me'] as const,
};
export const feedQuery = (f: FeedFilters) =>
  queryOptions({
    queryKey: profileKeys.feed(f),
    queryFn: () => profileApi.getFeed(f).then(mapFeedDtoToModel),
  });
```

- Мутации живут в `features/*`, инвалидируют ключи сущностей, где уместно используют оптимистичные обновления с откатом (save/unsave, skip, отправка сообщения).
- Настройки по умолчанию: разумный `staleTime`, `retry` не для 4xx, `gcTime`, `refetchOnWindowFocus` по месту.

### 7.4. Zod

- Схемы форм рядом с фичей (`features/edit-profile/model/schema.ts`), тип через `z.infer`.
- DTO → доменная модель через мапперы в `entities/*/api/mappers.ts`. Компоненты зависят от доменных моделей, а не от формата бэкенда.
- Валидация ответов Zod включается на критичных и нестабильных эндпоинтах (мэтчи, доступ, WS-события) и по флагу в dev; расхождения логируются в Sentry без ПДн.

### 7.5. Авторизация

- Сессия в `httpOnly` cookie, выставляемой бэкендом (или BFF-слоем `app/api/*`, если бэкенд на другом домене: проксирование убирает CORS и не хранит токены в JS).
- `middleware.ts`: guard для `/connect/*` (кроме `/connect/login`), `X-Robots-Tag: noindex, nofollow`.
- `entities/viewer`: текущий пользователь + **abilities** (набор возможностей, а не булев paid): `canSendInterest`, `canChat`, `canBook`. Хук `useAbility()` и компонент `<Can ability="canChat">` единообразно управляют доступом и открывают paywall из одного места.
- OTP: `features/auth-by-email` (шаг 1 запрос кода, шаг 2 ввод кода, таймер повторной отправки, обработка лимитов, ошибка неверного кода).

## 9. Реальное время (WebSocket)

Из макета не ясно, будет ли чат на WS или на polling (есть кнопка «Обновить сообщения»). Поэтому **транспорт заменяемый**: компоненты общаются с хуком `useConversation(matchId)`, а не с сокетом напрямую.

### 9.1. `shared/api/ws-client.ts` (универсальный, без доменов)

- Состояния: `idle | connecting | open | reconnecting | closed`.
- Reconnect: exponential backoff + jitter, максимум попыток, сброс при успешном открытии.
- Heartbeat (ping/pong) и обнаружение «тихого» обрыва.
- Авторизация через одноразовый ticket: `POST /api/ws-ticket` → `wss://…?ticket=…` (токен в URL не кладём).
- Подписки по типам событий/каналам с возвратом `unsubscribe`; очистка при unmount.
- Пауза/возобновление по `visibilitychange` и `online/offline`.
- Покрыть юнит-тестами с фейковым сокетом (reconnect, heartbeat, подписки, очистка).

### 9.2. Типизация событий

```ts
const WsEvent = z.discriminatedUnion('type', [
  z.object({ type: z.literal('message.created'), payload: MessageDto }),
  z.object({ type: z.literal('match.created'),   payload: MatchDto }),
  z.object({ type: z.literal('access.updated'),  payload: AccessDto }),
]);
```

Неизвестные события логируются и игнорируются, не роняют клиента.

### 9.3. Мост в кэш (`entities/message/model/realtime.ts`)

- `message.created` → `setQueryData` нужного разговора, увеличение счётчика непрочитанных, если чат не открыт.
- `match.created` → инвалидация списка мэтчей, тост.
- `access.updated` → обновление `viewer` и abilities (paywall исчезает без перезагрузки).

### 9.4. Сообщения

- Отправка оптимистично, с `clientId` для дедупликации эха с сервера; статусы `sending | sent | failed` и кнопка «Повторить».
- История: `useInfiniteQuery` с cursor-пагинацией, сохранение позиции прокрутки при подгрузке старых, автопрокрутка вниз только если пользователь у низа.
- Сообщения рендерятся **только как текст** (никакого `dangerouslySetInnerHTML`), ссылки опционально через безопасный линкификатор.

### 9.5. Фолбэк

Если сокет недоступен или `CONNECT_CHAT_ENABLED` в режиме polling, `useConversation` переключается на `refetchInterval`. Для UI разницы нет. Кнопка «Обновить сообщения ↻» остаётся как ручное обновление.

Провайдер сокета живёт в layout CONNECT, поднимается только после авторизации, закрывается при выходе.

## 10. Формы

- RHF + `zodResolver`, режим валидации `onTouched` (или `onBlur`), `reValidateMode: 'onChange'`.
- Единый `Field` (label, hint, error, `aria-describedby`, `aria-invalid`), одинаковый для всех форм.
- Маппинг серверных ошибок на поля: `ApiError.fieldErrors` → `setError`.
- Профиль: `TagGroup` с лимитом 8 и сообщением при превышении; два согласия раздельно и без предзаполнения; кнопка сохранения disabled при невалидной форме/во время запроса; защита от потери данных (`beforeunload` и перехват внутренних переходов при dirty-форме).
- Поле «Сайт»: валидация URL, только `http(s)`, нормализация, безопасный вывод (`rel="noopener noreferrer nofollow"`).
- Статус профиля в `entities/profile`: `draft | pending | approved | rejected`, с таблицей соответствия статус → бейдж → текст (никаких разрозненных `if`). Изменение существенных полей возвращает профиль на модерацию (показывать пользователю).
- Удаление аккаунта: подтверждающая модалка, явное описание последствий.

## 11. Ошибки, загрузка, пустые состояния

- `error.tsx` и `loading.tsx` на уровне route groups; Error Boundary на уровне виджетов (падение чата не должно ронять ленту).
- Таксономия ошибок: сеть, 401, 403 (билет), 404, 422 (поля), 429, 5xx. Для каждой своя реакция (inline / тост / paywall / редирект).
- Skeleton'ы повторяют форму реального контента (без «скачков» layout).
- Empty states переиспользуемым компонентом (лента закончилась, нет сохранённых, нет мэтчей, нет встреч, нет сообщений).
- Оффлайн-индикатор в CONNECT.

## 12. Производительность, a11y, безопасность

**Производительность**
- Лендинг SSG, серверные компоненты по умолчанию; `'use client'` минимально.
- `next/font` (локальные шрифты с `display: swap`, subset кириллицы), `next/image` с заданными размерами/пропорциями (нет CLS), `priority` только для LCP.
- `LazyMotion` + `domAnimation`, динамический импорт тяжёлого, уважение `prefers-reduced-motion`.
- Бюджеты: LCP ≤ 2.5 s, CLS ≤ 0.05, INP ≤ 200 ms на мобильном профиле; Lighthouse CI в пайплайне.
- Мобильная вёрстка: `dvh`, `env(safe-area-inset-*)`, нет горизонтального скролла на 360–430 px.

**Доступность**
- Семантические теги (`header`, `nav`, `main`, `section` с `aria-labelledby`, `footer`), один `h1`, правильная иерархия заголовков (в макете заголовки капсом это стили, а не обязательно CSS `uppercase`; используй `text-transform: uppercase`, чтобы скринридеры читали нормальный текст).
- Клавиатурная навигация, `:focus-visible`, фокус-трап и возврат фокуса в модалках, `aria-live` для тостов и новых сообщений, `skip to content`.
- Контраст AA, цель касания не менее 44×44 px на мобайле.
- axe-проверки в e2e на ключевых экранах.

**Безопасность и ПДн**
- CSP и security-заголовки в `next.config` (X-Content-Type-Options, Referrer-Policy, frame-ancestors, Permissions-Policy).
- Cookie: `httpOnly`, `Secure`, `SameSite=Lax/Strict`.
- Сообщения и поля профиля выводятся как текст, URL санитизируются.
- В Sentry/аналитику не отправлять email, имена, тексты сообщений (scrub в `beforeSend`).
- Баннер cookies и подключение Метрики только после согласия.
- Согласия: хранить факт и версию документа (отправлять на бэкенд вместе с формой, если API это поддерживает).
- Юридические страницы-заглушки с пометкой «текст предоставит заказчик», тексты в контент-файлах.

## 13. Тестирование и качество

- **Vitest:** схемы Zod, мапперы, ws-клиент, query-хуки, утилиты, ключевая логика abilities и статусов профиля.
- **Testing Library:** формы (профиль, вход, OTP), paywall-модалка, `TagGroup`, чат-ввод.
- **Playwright e2e (минимум):** (1) лендинг: навигация по якорям, FAQ, CTA; (2) вход через OTP; (3) заполнение профиля и сохранение; (4) лента: skip / save / «Хочу познакомиться» → paywall без билета; (5) с билетом: интерес → мэтч → чат (с MSW WebSocket-моком); (6) мобайл-viewport 390 для лендинга и CONNECT.
- **MSW:** единый набор хендлеров (REST + WebSocket) используется в dev (`NEXT_PUBLIC_API_MOCKING=enabled`), Vitest и Playwright. Моки должны возвращать демо-данные из макета (Мария (демо), Анна (демо)) и покрывать сценарии: нет билета, есть билет, ошибки, 429, оффлайн.
- **CI (GitHub Actions):** install (кэш) → typecheck → lint (ESLint + Steiger) → unit → build → e2e → Lighthouse CI.
- **pre-commit (lefthook):** lint-staged, typecheck изменённого, commitlint.
- **Скрипты:** `dev`, `build`, `start`, `lint`, `typecheck`, `test`, `test:e2e`, `storybook`, `api:types`.

## 16. Допущения по умолчанию (если не уточнено)

- **Бэкенд:** контракта нет. Работаем на MSW; в `docs/api-contract.md` описываем ожидаемый контракт, его потом согласуют с бэкендом. Адрес API из `NEXT_PUBLIC_API_URL`, при необходимости через BFF.
- **Сессия:** `httpOnly` cookie, ставит бэкенд.
- **Чат:** сначала polling (интервал 5–10 s), WebSocket как улучшение (этап 6). Протокол событий из раздела 9.2.
- **Билетный оператор:** ссылка «Билеты» ведёт на URL из `links.ts` (заглушка). Синхронизация доступа через `viewer.abilities`, которые приходят с бэкенда.
- **Формы лендинга** (партнёр, пресса, спикер) пока ссылки/`mailto:`.
- **Бронирование встреч** не реализуется, только заглушка по флагу.
- **Фото площадки и логотип:** временные ассеты из PDF, помечены в `docs/assets-todo.md`.
- **Юридические тексты:** заглушки в контент-файлах.
- **Хостинг:** Docker standalone, без привязки к платформе; без Vercel-специфики.
- **i18n:** не нужен (только русский), но строки не хардкодятся в JSX, что оставляет путь к локализации.
